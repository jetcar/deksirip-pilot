# Спецификация технического прототипа

Статус: Draft 0.1. Это спецификация исследовательского прототипа, а не
готовая государственная информационная система. Прототип должен позволить
проверить цепочку «ресурс — решение — действие — аудит» на малом добровольном
пилоте.

## 1. Границы прототипа

Прототип обслуживает один локальный пилот и ограниченный набор ресурсов:
например, продукты, свободные помещения, производственные часы и резерв.
Он не заменяет государственную регистрацию личности, бухгалтерию, медицину или
суд. Внешние системы подключаются через экспортируемые записи и ручное
подтверждение.

## 2. Основные сущности

Минимальная модель данных:

| Сущность | Что фиксируется |
|---|---|
| `PersonCredential` | право участия, базовые права, статус доступа; персональные данные отдельно |
| `Asset` | склад, помещение, оборудование, инфраструктура, ответственный контур |
| `ResourceBatch` | вид ресурса, количество, единица, качество, место, срок годности |
| `Capacity` | мощность, доступные часы, ограничения и подтверждающий источник |
| `Request` | кто и зачем запрашивает ресурс, срок, объём, приоритет, альтернативы |
| `Reservation` | условное закрепление ресурса, срок действия, условия отмены |
| `Project` | цель, план, ресурсы, этапы, риски, метрики и план выхода |
| `Vote` | вопрос, варианты, правила участия, сроки, методы проверки подсчёта |
| `Decision` | результат, меньшинство, применённое правило, срок действия |
| `LedgerEvent` | неизменяемое событие с автором, временем, ссылками и хешем |
| `AuditFinding` | проверка, доказательства, нарушение, исправление, ответственный |
| `AIAnalysis` | вопрос, источники, допущения, модель, расчёт, неопределённость |

## 3. Инварианты

Система считается корректной только если:

1. Любое физическое движение ресурса связано с событием журнала: источник,
   получатель, количество, время, подтверждение и остаток после операции.
2. Цифровой остаток не может превышать подтверждённый физический остаток.
3. Бронь не является окончательной передачей: она истекает, отменяется или
   превращается в подтверждённую поставку отдельным событием.
4. Голос не меняет ресурс напрямую. Он создаёт решение, а действие выполняется
   отдельной операцией с проверкой полномочий, правил и доступного баланса.
5. Один человек получает один действительный голос в рамках одного вопроса;
   повторные, отозванные и просроченные голоса проверяемо исключаются.
6. Каждое решение ссылается на правило, версию исходных данных, расчёт и
   физические последствия.
7. Закрытые персональные данные не публикуются; публичный аудит получает
   агрегаты и доказательство права, а не лишние сведения о человеке.
8. Временный аварийный мандат имеет срок, область действия и обязательный
   аудит после завершения.
9. Журнал событий добавляется, но не переписывается. Исправление оформляется
   новой записью с причиной и ссылкой на исходную ошибку.

## 4. Разрешённые операции

Операции прототипа должны быть явными и журналироваться:

```text
register_asset(asset, evidence)
publish_stock(batch, evidence)
publish_capacity(capacity, evidence)
submit_request(request)
reserve_resource(request, allocation, expiry)
record_delivery(reservation, physical_confirmation)
record_use(delivery, quantity, evidence)
propose_project(project)
open_vote(proposal, rules, closing_time)
cast_vote(vote, proof_of_eligibility)
close_vote(vote, tally_proof)
release_tranche(project, stage, resource_plan)
audit_event(event_range, auditor)
ask_ai(question, data_snapshot, model_version)
```

ИИ не имеет разрешений `cast_vote`, `close_vote`, `record_use`,
`release_tranche`, `edit_event` или `publish_decision`. Он может только читать
разрешённый срез данных и создавать подписанный аналитический отчёт.

## 5. Состояния процессов

Проект: `draft → reviewed → voted → active → paused/completed/cancelled`.

Переход обязан указывать автора, правило, доказательства и последствия. Переход
`active → cancelled` не удаляет историю и не освобождает уже использованный
ресурс задним числом.

Голосование: `draft → public_review → open → closed → challenged/confirmed`.
Оспаривание запускает проверку, но не подменяет исходный результат новой
записью.

## 6. Контракт ИИ-помощника

Каждый ответ ИИ должен содержать:

- использованный снимок данных и дату;
- ссылки на исходные записи и применённые правила;
- допущения, диапазон неопределённости и известные пробелы;
- версию модели и краткий журнал преобразований;
- альтернативный сценарий и аргумент против основной рекомендации.

Для решений, влияющих на базовые услуги, ИИ обязан показать минимум два
сценария и группу возможных проигравших. Пользователь может открыть исходные
данные, повторить расчёт и отправить ответ на человеческую проверку.

## 7. Приватность и устойчивость

- личность, право голоса, медицинские сведения и экономические операции
  хранятся в разделённых контурах;
- для тайного голосования используется отделённое доказательство права, а не
  публичная связь личности с выбором;
- бумажный и очный канал являются равноправным резервом;
- офлайн-события подписываются локально и попадают в общий журнал после
  сверки конфликтов;
- независимые копии журнала не должны находиться под контролем одного
  оператора;
- критические выгрузки должны быть читаемы без закрытого программного сервиса.

## 8. Приёмочные проверки

Прототип нельзя считать готовым, пока независимый проверяющий не подтвердит:

1. невозможно незаметно создать ресурс из воздуха или потратить больше остатка;
2. невозможно проголосовать дважды или восстановить выбор другого участника;
3. любой опубликованный результат воспроизводится из сохранённого снимка данных;
4. ИИ не может изменить журнал, проголосовать или выполнить распределение;
5. после исправления ошибка остаётся видимой в истории;
6. при отключении сети можно продолжить работу по резервному сценарию и
   обнаружить конфликт при синхронизации;
7. участник может проверить право голоса, результат и относящиеся к решению
   ресурсы без доступа к чужим персональным данным;
8. аварийный мандат автоматически прекращается и создаёт обязательное дело
   последующего аудита.

Результаты каждой проверки публикуются как тестовый отчёт: входные данные,
действия, ожидаемый результат, фактический результат и найденные ограничения.
